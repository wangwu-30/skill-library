# Purpose
让第一次接触项目的工程师或决策人读一遍就能答出三件事：提议做什么、要他拍板什么（有哪些选项）、最大风险是什么。只改结构和表达，不改事实。

## When To Use
- 已有一份技术方案草稿（通常是 Codex 先写好的），需要改写成易读版本。写和改分两步做：本 skill 只负责“改”。
- 不用于：博客/公众号/即刻/X（场景=博客）、周报/汇报（场景=汇报）、API 参考文档、从零起草方案。

## Inputs
- `plan`：原方案全文（唯一事实来源）。
- `glossary`：项目 glossary 的路径（比如 `docs/glossary.md`），是项目对术语的共识。缺省时先找仓库里的 `GLOSSARY.md`、`docs/glossary.md`；都没有就当作空 glossary。
- 可选：读者（默认是熟悉技术、但不了解这个项目的工程师）。

## Workflow
1. 读原方案，列出它的事实清单（数字、选项、风险、依赖、时间、不改什么）。改写时这份清单只能搬位置，不能增删改。
2. 读 glossary。改写中每个专有名词、缩写、内部代号都按下面处理：
   - glossary 里有：照用 glossary 的写法，第一次出现时不用另外解释；
   - glossary 里没有：要么改成平白的说法，要么保留，并在文末「术语提案」里列出“术语 — 一句话定义 — 为什么需要”，等人审。不能悄悄自创新术语。
3. 按下面的骨架重排（没有内容的节写“无”，不能省略）：
   ```
   标题 ｜ 状态 ｜ 日期
   0. 结论：一句话，说清提议做什么、预期收益（有数字就带数字）
   1. 需要拍板的事：表格（问题 / 选项≥2 / 推荐 / 不选推荐的代价），按重要性排
   2. 背景与目标：现状事实、目标、非目标
   3. 方案：先一段概述，再列改动点（组件 → 改什么），并明确列出“不改什么”
   4. 备选方案与为什么不选
   5. 风险与缓解：第一条是最大风险，并标注「最大风险」
   6. 上线与回滚
   附录：参数、配置值、key/schema、路径、代码、指标等细节
   术语提案（如有）
   ```
4. 文体：中性、陈述句、第三人称或“我们将……”。不用第一人称叙事、设问、感叹、比喻和排比口号，不寒暄。表格和清单该留就留，不要改成散文。
5. 正文放判断和取舍，实现细节放附录。长度不设硬上限，但正文里不要重复附录的内容。
6. 自查：对照事实清单逐条确认；结论在第一节；每个待拍板项至少有 2 个选项和一个推荐；非 glossary 术语都已经改成平白说法或列进了术语提案。

## Output Contract
只输出改写后的 Markdown 文档，不附说明。原文里的每个事实都能在改写版里找到；原文没有的事实一个都不加。

## Validation
- 可以用 `scripts/report.py <doc> --glossary <path>` 生成一份**参考报告**（骨架各节是否齐全、glossary 外的术语、是否带博客腔），只供评测和自查参考，**不作为通过与否的门槛**。
- 事实保真要靠人或另一个模型逐条对照事实清单检查。
